every action is just message passing, including gathering the data. there should
not be a special node indicated internally as the head; every node should have the
same potential.

nodes are told what to do by a stack of messages that is built at the start,
then sent out via the indicated entry point. with each newly encountered node, the
stack pops a message based on whether the top message should be recieved by said
node.
stack can look like this
[
{msg0, [node0]}
{msg1, [node0, node1]}
{msg2, [node3]}
...
]
at the end of the stack, a list of nodes and files/directories specified by the user can be traversed to gather data

there will have to be a node that acts as an entry point. visually, the software should be able to generate a directed graph

from that point, it will be assumed that every node listed within the
experiment will be used.
	   -> if a node is not to be used, it should be set to NA, otherwise an
	   error will be given to the user.

assumed that the entry node will gather the data.
	-> there has to be a way for the user to specify files/dirs where
	data will be saved
	- if assumption is bad, give users a way to specify some node or
	as a data-gatherer. can be thought of as an integration into
	the directed graph.
	- users can be given a way to specify on which instances data are
	collected (one or many)

give dsl way to make a command standing? for instace, "gather data 30s &" where
'&' creates a daemon that loops the command indefinetly.

can clump nodes, so that a single edge hits all of them. clumps can contain clumps.
clumps are not gauranteed to recieve their message in any particular order

first pass
      - clump any nodes that need to be
      - set some node or clump as the head
      - set rest of edges
      - the head and each edge sends some command, like bash or DSL ("wait 30s")
      - edges can be self-loops
